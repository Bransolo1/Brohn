# Study material authoring audit

20 September 2026. Read-only source and retained-evidence review; no new browser or scientific worker run was performed for this audit. The complete 50-capability register remains intended scope, not 50 currently enabled participant procedures. Study templates select a design; checking a measurement does not activate a new material renderer.

The findings below preserve the pre-implementation snapshot. The subsequently
authorized passive/exemplar editor is documented in

Imported/retained passive media have a wider allowlist than the upload UI. Portable designs allow PNG/JPEG/WebP, WAV/MP3/OGG, MP4/WebM; participant delivery additionally allowlists GIF and several audio/video MIME variants. **GIF is not currently in the portable ZIP format list.** Plan nevertheless routes every non-null passive asset through `brohn_asset_data_uri`, which accepts only PNG/JPEG up to 5 MiB. Thus a permitted imported WebP/audio/video asset cannot receive an appropriate Plan preview through this path. This is a code-level incompatibility, not a newly executed browser reproduction. No authoring claim for arbitrary audio/video uploads follows from the delivery allowlist.

## Validation, authority and recovery findings

All current researcher image upload paths use `new_png_asset`: readable original bytes, at most 5 MiB, 4096 pixels per side and 8 million pixels, validated signature/header plus complete PNG decoding. Immutable objects keep a SHA-256 identity. Clone/template reuse retains assets; portable export verifies exact hashes and excludes participant/results records. Participant asset GET checks the material belongs to the retained release; it is not a general object download.

The older passive/task observers in `platform-app.R` remember only stimulus ID or task/material IDs, then attach to `current$study` when the upload event arrives. They do not pin the opening study, revision, design hash, project and target hash, nor distinguish a fresh file transfer from a previous dialog. Normal save revision checks do not substitute for that missing dialog context. This is a source-review finding requiring focused stale-dialog tests; no cross-study browser exploit was executed. Upload errors currently reach the global page alert rather than a dedicated material-dialog error.

Welcome already provides the stronger pattern: explicit attach, fresh transferred-file requirement, current study/revision/design checks, local error preservation, image replacement/removal and failure recovery. Failed passive/task media preload conservatively interrupts the session; it does not silently replay timed trials. Welcome image retry occurs before any participant session starts.

## Recommended next slice: pinned material editor

**Implement a common PNG editor for passive stimuli and the existing IAT/BIAT/keyboard-AAT exemplars.** This improves an already enabled upload path without adding a scientific procedure or a file format. Questionnaire/MaxDiff inline images remain explicit follow-on schema work.

Proposed contract, pending the coordinator's checkpoint go-ahead:

1. **Context and atomic save.** A dialog pins study ID, saved revision/design hash, project, target kind/ID and target hash. Attach/replace/remove recheck this context, archive state and current authority. Only a fresh completed file transfer can be committed. Invalid bytes, stale state or cancellation preserve the current material and unsaved dialog text; errors and recovery instructions stay in the dialog.
2. **Descriptions without legacy mutation.** Add optional `image_alt` to passive stimuli and task materials, populated only by explicit new authoring. Require a useful description for new/replaced images. Do not inject defaults into old designs or retained protocols. Legacy participant fallbacks stay unchanged: passive **Study image**, task `content` or **Task image**. New compiled copies retain the explicit description. Task IDs, category membership, allocation, timing, scoring and registry semantics stay unchanged.
3. **Visible material review.** Show filename, native type/dimensions and a source-bound preview action instead of hash-only task content. Preview one exact saved material at a time using its original bytes and protocol appearance. It creates no release, allocation or response. Editing a description preserves the asset hash and AOIs; replacing different passive image bytes clears current AOIs explicitly.
4. **Remove or return to text.** Make the action explicit. Passive removal clears the image/AOIs and returns to editable text, with incomplete text visible in readiness. A task exemplar must retain a valid nonempty text replacement; never save an invalid image-less task material or silently remove category support.
5. **Existing media types remain reviewable.** Dispatch previews by actual validated media type. PNG/JPEG/WebP/GIF use an image element; allowlisted retained audio/video use native controls. Use a bounded session-bound resource route tied to the current project/material, with exact object verification; do not base64-hydrate large media or expose arbitrary hash downloads. Unsupported/unavailable media gets an actionable retained-file state. Do not route audio/video through PNG decoding or offer image AOI controls for them. Preserve the existing portable format list, including its GIF exclusion.
6. **Focused acceptance.** Actual authoring → invalid upload/recovery → preview/description → sample release → exact participant bytes/description → replacement with old release preserved → clone/template/ZIP reuse. Include stale revision/navigation/reopened-file tests, remove/text recovery, AOI invalidation, legacy hash/timeline invariance, all three exemplar task families, intentional fixed-RT exclusion and desktop/390-pixel keyboard/accessibility checks. Separately render permitted imported image/audio/video types without claiming codec or hardware timing qualification.

Proposed ownership: new `R/platform-materials.R`, `R/platform-material-views.R`, focused domain/Shiny/browser fixtures/tests; scoped passive/task view, validator, participant renderer and portability regression changes. Coordinator owns replacing the two old app upload observers and loader/installer wiring. Proposed installer: `brohn_install_materials(input, output, session, store, current, state, attempt, capture, update_study)`; proposed card helper accepts an explicit target kind and stable target IDs. Exact preview resource details are to be settled before implementation. No production edits were made for this audit.
