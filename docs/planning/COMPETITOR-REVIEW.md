## Strategic finding

**I:** The primary operator is now an undergraduate psychology researcher: design for a novice who needs to run an eye-tracking study quickly and understand the results. The opportunity is a connected workflow: research question → complete validated recipe → stimuli → signal checks → collection → AOIs and preprocessing → versioned scoring → understandable report. Commercial deployment remains a use case, not the assumed level of operator expertise. A claim that competitors cannot do implicit experiments would be false: Inquisit has extensive ready templates; Gorilla and Labvanced combine visual builders with ready examples; CloudArmy packages consumer decisions around implicit and other fast behavioural methods. Differentiate through fewer manual handoffs, visible analysis provenance, and reusable study/report recipes. Measure the improvement through observed time-to-first-valid-pilot, task success without help, comprehension and analyst time-to-reviewed-report.

### Novice UX implications (proposal)

- Start at **“Run an eye-tracking study”** with complete recipes such as compare two images, inspect a webpage, watch a video, find an item on a shelf, or test a hypothesis about an area. The first experience should not require construction of trial loops, object events or signal-processing pipelines.
- Make the default path five understandable workspaces: **Plan → Questions → Collect → Review → Results**. Keep Design/AOIs/Signals/Analysis as deeper controls within that same study, with a persistent plain-language summary of what will happen.
- After upload, propose semantic AOIs and a study sequence; the researcher reviews a visual plan. Explain “area of interest” beside a concrete labelled object before introducing the acronym.
- Put hardware/camera setup into a guided check: connection, positioning, calibration, validation, short pilot. Explain the next corrective action in context and distinguish participant setup problems from missing or noisy data.
- Provide a sample-data preview before collection. The novice should see what a result means, what would support their hypothesis and what would remain uncertain before pressing Start.
- Use progressive disclosure for randomisation, timing, filters and scoring parameters; preserve an advanced mode and reproducible defaults without making those prerequisites for a first successful study.
- Evaluate with actual undergraduates: first valid study without help; critical errors; clicks and backtracking; calibration recovery; correct interpretation of gaze versus liking; understanding of excluded participants; accessible keyboard and screen-reader paths. Compare the same complete recipe across platforms, not isolated visual widgets.

## Concrete patterns to carry into the UI specification

**Gorilla — D:** screen creation exposes blank/instructions/two-choice templates and optional scoring/time limits. The editor separates preview, object list and inspector; its debug panel exposes event order while previewing a specific trial row. Experiment controls provide branching and randomisation, while activity versions can be fixed or auto-updated. **I:** retain an expert canvas and event debugger, but present a recipe-level contract first: stimulus categories, response mapping, sampling, counterbalance, checks, and expected outputs. Show exactly which changes invalidate the scoring recipe. Sources: [Task Builder 2](https://support.gorilla.sc/support/tools/task-builder-2/how-to), [Experiment Builder](https://support.gorilla.sc/support/tools/experiment-builder/how-to), accessed 2026-09-05.

**Labvanced — D:** the sidebar distinguishes main workspace navigation from study-specific tabs. Its data export has Recordings, Variables and Export Format views; users can save column selections, preview exact output, separate sessions/trials/timeseries, and export the experiment specification. **I:** connect this clarity to a live data contract before recruitment, including units, missingness, raw/derived provenance and expected per-task outputs. Sources: [Guide](https://www.labvanced.com/content/learn/en/guide/), [Dataview and Export](https://www.labvanced.com/content/learn/en/guide/data-export/), accessed 2026-09-05.

**PsychoPy — D:** a Routine is a track-based time view and Flow controls the order/repetition of routines. **I:** our task editor should offer both a readable sequence and a frame-level timeline. Advanced temporal controls should not require every marketer to understand frame scheduling. The builder should explain incompatible requested durations and log observed timing. Sources: [Builder concepts](https://psychopy.org/builder/concepts.html), [Routines](https://psychopy.org/builder/routines.html), [Online compatibility](https://psychopy.org/online/check-online-compatibility.html), accessed 2026-09-05.

**RealEye — D:** AOIs can contain multiple shapes, be copied/imported between items, and yield automatic statistics and side-by-side reports. Live-page dynamic AOIs can be tied to HTML attributes. **I:** design one AOI workspace that combines semantic suggestions, temporal tracking, DOM-bound regions, reusable labels and a review queue; save the proposed and approved geometry separately. An AOI is part of the research hypothesis and analysis version, not merely an overlay. Sources: [AOIs](https://support.realeye.io/what-is-aoi), [Dynamic AOI example](https://app.realeye.io/doc/examples/live-website-dynamic-aois.html), accessed 2026-09-05.

**CloudArmy — D/V:** methods are explained by the decisions they answer. Its science page distinguishes association, timed intuitive choice, findability, self-report, modelled saliency and measured webcam gaze, with interpretation boundaries. **I:** start the product with questions such as “Which concept communicates our attribute?”, “Will the claim be noticed?”, and “Which pack is found fastest?”. Keep the individual signals accessible beneath the integrated report. Source: [Methods](https://cloud.army/about/science/), accessed 2026-09-05.

## Automation and multimodal requirements informed by evidence

1. **I: Recipe manifests.** A recipe packages design constraints, participant instructions, allowed devices, stimuli schema, randomisation, QC, scoring code, report sections and method references. A clone receives a new version; research data retain the exact recipe version.
2. **I: Preflight as a simulation.** Generate synthetic participant paths, balance counts and expected rows; validate missing assets, response mappings, reachable exits and score completeness before pilot collection. Make each failure clickable in the builder.
3. **I: Two runtime classes.** Browser consumer testing and validated lab capture share study definitions and events but have explicit capabilities. R should orchestrate and analyse; do not put trial timing across Shiny server round trips. Exact architecture should be benchmarked against device/browser conditions.
4. **D → I: Synchronisation contracts.** Labvanced's EEG walkthrough enables LSL, names the marker stream and emits markers from event logic. Our design needs study/trial/stimulus/response markers plus clock-domain mapping, measured offset/drift and observable dropped samples. A supported connector is not proof of valid cross-device timing. [EEG walkthrough](https://www.labvanced.com/content/learn/en/walkthroughs/2025-01-desktop-app-study-with-eeg-integration/), accessed 2026-09-05.
5. **D → I: AOIs as reusable data.** Labvanced uses invisible polygons/SVGs for exact-boundary gaze/fixation checks. Our model should unify polygons, time-varying masks, DOM regions, semantic labels and review history; support one ontology across stimulus versions. [Labvanced AOIs](https://www.labvanced.com/content/learn/en/guide/webcam-eye-tracking/areas-of-interest-aoi), accessed 2026-09-05.
6. **I: Analysis does not stop at scores.** Produce trial/participant exclusions with reasons, distribution checks, reliability diagnostics, contrasts and uncertainty, sensitivity analyses, cross-signal alignment views, and an editable claim-evidence report. Reports must describe what was measured rather than assert a single hidden “emotion” or “preference” from any signal.
7. **I: Repeated research operations.** Reuse assets and semantic AOIs; compare versions; template cohorts and sampling; rerun only invalidated downstream outputs when new data or a reviewed AOI arrives. Make completion observable and failures resumable.

## Evidence caveats that change implementation decisions

- **D:** precision of a software clock is different from delivered stimulus timing; hardware, display refresh, OS and input-device latency matter. PsychoPy explicitly recommends measurement with external timing hardware. **I:** ship a timing certification harness and publish measured supported configurations rather than repeat an unqualified “millisecond accurate” claim. [PsychoPy timing guidance](https://psychopy.org/general/timing/millisecondPrecision.html), [timing overview](https://devdocs.psychopy.org/general/timing/index.html), accessed 2026-09-05.
- **D:** Gorilla's documentation maps gaze samples to object coordinates and its release notes describe a corrected normalised-coordinate issue. **I:** retain immutable raw gaze and transformation versions, and add coordinate-system golden tests across screen sizes, aspect ratios and origin conventions. [Eye tracking](https://support.gorilla.sc/support/tools/task-builder-2/eye-tracking), [release notes](https://support.gorilla.sc/support/gorilla-reference/release-notes), accessed 2026-09-05.
- **D:** RealEye's general dashboard FAQ says it does not generate reports, while its specific AOI documentation says AOI comparison reports download as CSV/PDF. This is a documentation conflict; use the specific AOI evidence, and verify current product scope in a live demo. Do not list report generation as absent.
- **D:** Inquisit's current BIAT manual contains a notice directing nonscholarly users to Project Implicit. **I:** add a commercial-redistribution review per paradigm and stimulus pack before open-source release; this notice is not a legal determination about present patent status. Templates, trademarks, software code and stimuli have separate provenance/permission requirements. [BIAT manual](https://www.millisecond.com/library/v7/iat/briefiat/briefiat/briefiat/briefiat.manual), accessed 2026-09-05.
- **D:** the GNAT technical manual explicitly characterises its example as a demonstration requiring research-specific parameter choices. **I:** label templates as demo, research-ready validated version, or experimental variant; automation must not erase that distinction. [GNAT manual](https://www.millisecond.com/library/v7/gnat/gnat/gnat/gnatdemo.manual), accessed 2026-09-05.
